uikit

Three skills in one flow — init-design-system, prototype, implement — for coding agents (Claude Code, OpenCode, Codex) that take a product brief to a working feature. Each one reads what the last one wrote. /uikit:what routes you; the map below is the order it routes within.

Run it in this order

The map is the canonical routing truth; this is that map drawn. Optional first step: /uikit:setup once per repo, to record the approved system, stack, and flows location so the skills stop guessing.

  1. 1 /uikit:init-design-system

    Once per project, with a PRODUCT.md in the repo.

  2. 2 /uikit:prototype <feature>

    Once per feature on the roadmap. Checks the Mobbin MCP first, and ends by asking which new drift joins the design system.

  3. 3 /uikit:implement docs/flows/<feature>.json

    When a flow is approved. Builds it into the real app.

1init-design-system

Turns the product brief into a design system, rendered as a live dev route and authored as real components in the project's own stack.

/uikit:init-design-system

Stops to ask when

  • The stack is not React, Astro or Svelte. Those three get native components and a live route; anything else falls back to the static page plus tokens.css.

Takes

  • PRODUCT.mdVision, business model, audience. Shapes the one domain component only this product would build.
  • Tokens already in the repoDESIGN.md, tokens.json, tailwind.config.*, globals.css. Reused exactly; only gaps get filled.
  • Your stackRead from package.json. React (shadcn), Svelte (Bits UI) and Astro get a live route and components; other stacks fall back to the page.

Gives

  • /uikit/design-systemA live dev route rendering logo, color, type, spacing, radius, border, shadow, icons and the real components. Every value drawn, not described.
  • components/ui/*Components authored on those tokens — shadcn (React), Bits UI (Svelte), native (Astro) — plus the domain component.
  • A project that still buildsTypechecks with the new components in place, ready for the next skill to use.

Ships with these defaults unless you ask otherwise

Color
OKLCH only. One primary for actions, one accent for highlights; neutrals derive from the primary.
Spacing
4-point scale, nothing between the steps.
4 8 12 16 24 32 48 64
Type
About 1.2 modular scale. Weights 400 and 500.
Surfaces
Three-layer shadow-border. Five radius tokens, five shadow tokens.
Icons
HugeIcons, one set, sizes on the scale.
Motion
Named properties, ease-out, under 200ms.

Two rules never move, whatever you ask: WCAG contrast, and an accessible name on every control.

2prototype

Draws one feature start to end as a flow definition plus a dev route that renders every step from the real components, then asks which new drift joins the system.

/uikit:prototype <feature>

Stops to ask when

  • The Mobbin MCP isn't connected. You can connect it or continue on free sources.
  • No design system is found.
  • A screen needs a color, typeface, radius or shadow the system doesn't have.
  • The run ends: for each new drift, fold it into the design system or keep it as a one-off.

Takes

  • The live design system/uikit/design-system and the components it imports. Every screen starts from them. No Modal when there is a Dialog.
  • PRODUCT.mdThe roadmap line the feature implements, plus audience and voice.
  • Mobbin MCPHow shipped apps solved each step. Paid, and checked before any research starts.
  • docs/flows/*.jsonFlows already drawn. The closest is the starting point; a component it proposed is reused as a candidate.

Gives

  • docs/flows/<slug>.json + /uikit/flows/<slug>Every step and state as a screen, composed from the real components. Mock values.
  • Decisions with sourcesWhy each screen looks the way it does, and the shipped product it rests on.
  • Drift ledgerWhat the system didn't cover, why, and your answer on whether each one joins the system.
  • docs/flows/README.mdThe index of flows, plus the mock values every flow shares.

Other ways to run it

/uikit:prototype <feature>, <feature>One flow per feature, drawn one at a time.
/uikit:prototype update <flow> <change>Redraws or adds steps in a flow that already exists.
/uikit:prototype migrate <flow.html>Converts a legacy HTML flow to a definition and a route.
/uikit:prototype driftAsks again about drift still open: answered Decide later, or already open across several flows. How it works
/uikit:prototype <feature> --system <path>Uses a different path as the design system.

Writes to docs/flows/ and the dev flow area only. Candidates never enter the production component tree; promotion is the one exception.

3implement

Builds the flow into the real codebase, in the project's own stack, with zero design-system drift.

/uikit:implement docs/flows/<feature>.json

Stops to ask when

  • No approved design system exists, or two sources conflict.
  • The system lacks a component the flow needs. The system gets updated first.
  • A backend contract is missing. The UI gets built; the operation is reported as blocked.

Takes

  • docs/flows/<feature>.jsonThe definition and the dev route that renders it. A legacy docs/flows/*.html works too.
  • The approved design systemThe route, its tokens and the real components. --system <path> picks one.
  • Your codebaseFramework, routes, data, forms and tests, all kept as they are.

Gives

  • Native routes and componentsWritten in the project's stack. Not a copied HTML page, screenshot or iframe.
  • Every state wiredValidation, loading, empty, error, success and back. Success follows a real response, never a timer.
  • A reportChanged code paths, checks run with their results, substitutions made, anything blocked.

Done only after these ran

  • Build, typecheck and tests
  • Every step walked in a browser
  • Screenshots at phone and desktop widths
  • Contrast measured on the rendered page
  • Drift audit of the changed code

Recorded drift is still drift. A flow marked one-off or proposed is not permission to ship it.

How drift stays out

Drift is anything a flow draws that the design system doesn't already provide. Prototype may drift, as long as it writes it down in the ledger. Implement may not.

The fold-back questions

Every prototype run ends here, with no extra command. It asks about each new drift the run drew: one no other flow has, its second use, a one-off another flow now reuses, or a broken guideline.

  1. Tallies the files the run drew and picks out the new drift.
  2. Re-checks each one against the current system. A drift the system now covers is swapped for that component, not asked about.
  3. Recommends an answer: keep it as a one-off when it is minor or specific to this feature, fold it into the nearest component, or add it to the system when two or more flows use it.
  4. Asks one question per drift, recommendation first, with Decide later as an option. Nothing is applied before you answer.
  5. Applies your answers: a promoted candidate becomes a real component in the component set and the viewer, and every flow that used it switches to it. Then it checks each flow still renders.

Drift you answer Decide later, and drift already open across several earlier flows, waits for /uikit:prototype drift, which asks the same questions across every flow. Each run offers to go through that list before it ends.

VerdictWhat it becomesWhen implemented
promoteA new component in the real component set and the viewer. Every later flow imports it.Used, once it exists in the approved system.
foldA variant of a component the system already has.Used, once the variant exists.
one-offStays a candidate in the dev flow area.Swapped for an approved component, or blocked until the system covers it.
